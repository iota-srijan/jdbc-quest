The analogy

A restaurant kitchen with staff

Raw JDBC is cooking alone. For every dish you fetch a pan, light the stove, cook, wash the pan, put it away, and deal with every alarm yourself. The cooking is maybe a fifth of the work.

With kitchen staff, you only hand over the recipe, the ingredients, and how to plate each portion. The staff fetch pans from a shared rack, cook, wash up and put everything back. If something goes wrong, the alarm says what went wrong ("out of eggs", "oven broken") instead of one generic beep.

The rack only holds a fixed number of pans. When they're all in use, the next cook waits. If no pan comes back in time, they give up and report it.

Basics · the template idea

Who does each step?

Every database call follows the same fixed recipe. Spring runs the parts that never change, and you supply the parts that do. This is the Template Method idea, and it's where the name JdbcTemplate comes from. Guess each step, then check the map.

Core · where connections come from

DataSource: the "ask for a pan" door

With raw JDBC, your repository knew the URL, username and password, and dialled with DriverManager. A repository should care about students, not about how to log in to MySQL.

A DataSource is a Java interface (javax.sql.DataSource) with one important job: getConnection(). It's a connection provider, not a connection itself. Your repository asks it for a connection and doesn't know or care how it was made.

    private final DataSource dataSource;              // the door, injected

    public StudentRepository(DataSource dataSource) {
        this.dataSource = dataSource;
    }

Remember: DataSource ≠ connection pool. A pool can implement DataSource. HikariDataSource is one that does.

Core · connection pooling

The pan rack, live

Opening a real connection is slow: network, contact the server, check the password, create a session. Doing that for every request of a busy web app wastes time and can flood the database.

A pool opens a few connections once and lends them out. close() doesn't destroy the connection, it puts it back on the rack. Send requests below and watch. Then switch to "No pool" and send the same burst.

What comes back? Tap a cell

@Repository
public class StudentRepository {
    private final JdbcTemplate jdbcTemplate;
    private final RowMapper<Student> studentRowMapper = new StudentRowMapper(); // reuse one mapper

    public StudentRepository(JdbcTemplate jdbcTemplate) {
        this.jdbcTemplate = jdbcTemplate;
    }

    public boolean save(Student student) {
        String sql = "INSERT INTO students(name, email, age) VALUES (?, ?, ?)";
        int rowsAffected = jdbcTemplate.update(sql,
                student.getName(),    // 1st ?
                student.getEmail(),   // 2nd ?
                student.getAge());    // 3rd ?  (order must match!)
        return rowsAffected == 1;
    }
}
public List<Student> findAll() {
    String sql = "SELECT id, name, email, age FROM students";
    return jdbcTemplate.query(sql, studentRowMapper);   // [] when the table is empty
}
public Optional<Student> findById(Long id) {
    String sql = "SELECT id, name, email, age FROM students WHERE id = ?";
    try {
        Student student = jdbcTemplate.queryForObject(sql, studentRowMapper, id);
        return Optional.of(student);
    } catch (EmptyResultDataAccessException e) {   // ONLY "zero rows" means not found
        return Optional.empty();
    }
    // database down, bad SQL, etc. keep flying upward as real errors
}
public Optional<Student> findById(Long id) {
    String sql = "SELECT id, name, email, age FROM students WHERE id = ?";
    List<Student> students = jdbcTemplate.query(sql, studentRowMapper, id);
    return students.stream().findFirst();   // empty list → Optional.empty()
}
// Trade-off: queryForObject() states "exactly one row expected" more clearly.
// For primary-key lookups, both are fine if you understand how each behaves.
public boolean update(Long id, Student student) {
    String sql = "UPDATE students SET name = ?, email = ?, age = ? WHERE id = ?";
    int rowsAffected = jdbcTemplate.update(sql,
            student.getName(), student.getEmail(), student.getAge(), id);  // id is the 4th ?
    return rowsAffected == 1;   // 0 = no student with that id
}
public boolean deleteById(Long id) {
    return jdbcTemplate.update("DELETE FROM students WHERE id = ?", id) == 1;
}
Core · RowMapper

"Plate each portion like this"

A RowMapper answers one question: how does one row become one object? You write that once. Spring loops through the rows and calls your mapper for each one. Step through it.

StudentRowMappermapRow(rs, rowNum)called 0 times
// As a class: clearest while learning
public class StudentRowMapper implements RowMapper<Student> {
    @Override
    public Student mapRow(ResultSet rs, int rowNumber) throws SQLException {
        Student s = new Student();
        s.setId(rs.getLong("id"));
        s.setName(rs.getString("name"));
        s.setEmail(rs.getString("email"));
        s.setAge(rs.getInt("age"));
        return s;      // one row in, one Student out
    }
}
// As a lambda: RowMapper has one method, so this works
private final RowMapper<Student> studentRowMapper =
        (rs, rowNumber) -> new Student(
                rs.getLong("id"),
                rs.getString("name"),
                rs.getString("email"),
                rs.getInt("age"));

// Or let Spring match columns to setters by name:
private final RowMapper<Student> auto =
        new BeanPropertyRowMapper<>(Student.class);

The mapper has no changing state: it reads the current row and returns a new object. So one shared instance is safe to reuse.

Advanced · errors

Labelled alarms instead of one beep

Raw JDBC throws SQLException for everything: a typo, a duplicate email, a dead server. It's also checked, so every method must catch it or declare it. Each database also uses its own error codes.

JdbcTemplate catches it and throws a specific DataAccessException subtype. These are unchecked, so your code isn't forced to catch them, and they're the same whichever database you use. Pick a problem and flip the database.

    The one gotcha worth remembering

    "Not found" and "database broken" are different answers

    Wrong belief: "queryForObject() returns null when there's no row" or "just catch DataAccessException and return empty". It throws EmptyResultDataAccessException on zero rows. And catching the parent type hides real outages behind a friendly "not found".

    ✗ Hides outages
    try {
    return Optional.of(jdbcTemplate.queryForObject(sql, mapper, id));
} catch (DataAccessException e) {     // catches EVERYTHING
    return Optional.empty();          // DB down → "404 not found"
}
    ✓ Honest
    try {
    return Optional.of(jdbcTemplate.queryForObject(sql, mapper, id));
} catch (EmptyResultDataAccessException e) {  // only "zero rows"
    return Optional.empty();
}   // other failures keep propagating as errors

    Smaller traps

    1. Values in the wrong order. update(sql, age, name, email) compiles fine but puts the age in the name column. Order must match the ?s.
    2. new JdbcTemplate(). It has no DataSource. Inject the bean Boot configured.
    3. "DataSource means pool." It's only an interface. A pool is one possible implementation.
    4. "A bigger pool is faster." Not automatically. Too many connections can overload the database. Size it with load tests.
    5. BeanPropertyRowMapper on a class without setters or a no-arg constructor. Mapping fails or quietly leaves fields empty.
    Test yourself · answer out loud before opening

    Recall check

    1. What does Spring JDBC take off your plate, and what stays your job?

    Spring: getting the connection, creating the statement, binding values, running, looping rows, closing, translating exceptions. You: SQL, values in order, row mapping, and what the result means.

    2. Is a DataSource a connection? Is it a pool?

    Neither, necessarily. It's an interface that provides connections. A pool like HikariDataSource can implement it.

    3. With a pool, what does connection.close() do?

    Usually returns the connection to the pool for reuse instead of shutting it down.

    4. Predict: pool size 3, all 3 busy, a 4th request arrives. What happens?

    It waits. If a connection comes back within connection-timeout, it gets that one. Otherwise the pool throws an error (CannotGetJdbcConnectionException in Spring).

    5. Which method for: delete by id, list all students, find by id?

    update(), query(), queryForObject() (or query() + findFirst()).

    6. queryForObject() finds no row. What happens? And 3 rows?

    Zero rows: EmptyResultDataAccessException. More than one: IncorrectResultSizeDataAccessException. It never returns null for "not found".

    7. Why not catch DataAccessException and return Optional.empty()?

    It would report "student not found" when the database is actually down or the SQL is broken. Only EmptyResultDataAccessException means "not found".

    8. Why does exception translation help if you move from MySQL to PostgreSQL?

    Your code handles DuplicateKeyException etc., which Spring produces from either database's codes. With raw JDBC you'd rewrite checks for MySQL-specific error codes.
