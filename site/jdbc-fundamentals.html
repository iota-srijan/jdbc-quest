How a Java program talks to MySQL

Java and MySQL are two separate programs. JDBC is the standard way Java opens a line to the database, sends SQL, and reads the answer back. This page turns the 50-page notes into maps, animations and small labs you can poke at.

ConnectOpen a session with MySQL using a URL, username and password.
Send SQLUse a PreparedStatement with ? blanks for the values.
Read & clean upWalk the rows one by one, turn them into objects, then close everything.

The analogy

Phoning a shop in another country

You want stock information from a shop abroad. You can't just shout across the border. You need a phone, and someone who speaks the shop's language.

Every phone has the same buttons, so you already know how to use any of them. The translator plugged into the line converts your words into the shop's language and their answers back into yours.

You dial the number, wait for them to pick up, and then make requests. You can say a fixed sentence, or better, fill in a form with blanks so nobody misreads your values. They read the answer back one line at a time. When you're done, you hang up. If you forget to hang up, the line stays busy for everyone else.

Basics · the pieces and connecting

Four things people mix up

THE SHOPMySQL Server

Stores the data and runs your SQL. It must be installed and running before anything can connect.

A WINDOW INTO THE SHOPDBeaver

A desktop app for looking at tables and running SQL by hand. Installing it does not install MySQL.

THE TRANSLATORMySQL Connector/J

A Java library (a Maven dependency) that speaks MySQL's network language for your program.

THE PHONE BUTTONSJDBC API

Interfaces built into Java (java.sql). Your code uses these and never touches MySQL-specific classes.

Decode the phone number

Make the call

import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.SQLException;

public class Main {
    private static final String URL = "jdbc:mysql://localhost:3306/student_db"; // the phone number
    private static final String USERNAME = "root";
    private static final String PASSWORD = "your_password";  // real apps: never commit this

    public static void main(String[] args) {
        // DriverManager reads "jdbc:mysql:", finds the MySQL translator, dials, logs in
        try (Connection connection = DriverManager.getConnection(URL, USERNAME, PASSWORD)) {
            System.out.println("Database connected successfully");
        } catch (SQLException e) {                      // the call failed
            System.out.println("Message: " + e.getMessage());
            System.out.println("SQL state: " + e.getSQLState());
            System.out.println("Error code: " + e.getErrorCode());
        }                                               // try-with-resources hangs up for you
    }
}
Class.forName(...)?
Not needed any more. Since JDBC 4.0 the driver registers itself when its JAR is on the classpath.
Opening a connection
Is slow-ish: network + login. Much more expensive than new Student(). (This is why chapter 2 adds a connection pool.)
application.properties?
Plain DriverManager doesn't read it. That's a Spring Boot thing.

Core · running SQL

One call, many requests

A Connection is the open call. It isn't one SQL command. To say something, you create a statement from it: connection.createStatement() or, better, connection.prepareStatement(sql).

Then you pick how to send it, based on what you expect back.

flowchart TD
  Q{"What will the SQL give back?"}
  Q -- "Rows to read
SELECT" --> A["executeQuery()
returns a ResultSet"]
  Q -- "A count of changed rows
INSERT · UPDATE · DELETE" --> B["executeUpdate()
returns an int"]
  Q -- "Don't know in advance
user-typed SQL, stored procedure" --> C["execute()
returns a boolean"]
  C -- "true" --> D["first result is a ResultSet
getResultSet()"]
  C -- "false" --> E["it's a count or nothing
getUpdateCount()"]
Decision map. execute()'s boolean tells you the type of the first result. It does not mean success or failure.

Practice: pick the method

executeUpdate() result
1 = one row inserted/changed · 0 = nothing matched · more = many rows. CREATE TABLE usually returns 0.
Name is misleading
executeUpdate() runs INSERT and DELETE too, not just UPDATE.
Core · reading rows

The ResultSet is a finger moving down a list

A ResultSet is not a List<Student>. It's the shop reading rows back to you with a finger (the cursor) on the current line. The finger starts above the first row. next() moves it down one row and says whether there was a row there.

JDBC has no idea a row should become a Student. You read each column and build the object yourself. Watch the third row: its age is empty (NULL).

List<Student> students

Core · PreparedStatement

Fill in a form, don't glue strings

Gluing user input into SQL is like letting a caller dictate your sentence word for word. If their "name" contains a quote mark, they can end your sentence early and add their own commands. That's SQL injection.

A PreparedStatement sends the sentence with blanks (?) and the values separately. A value can never become SQL code, however strange it looks. Type into the box, or try the presets.

green = user text treated as data · red = user text that MySQL would run as SQL

String sql = "INSERT INTO students(name, email, age) VALUES (?, ?, ?)"; // the form

PreparedStatement ps = connection.prepareStatement(sql);
ps.setString(1, student.getName());   // blank #1 (numbering starts at 1, not 0)
ps.setString(2, student.getEmail());  // blank #2
ps.setObject(3, student.getAge());    // blank #3 · setObject handles a null age for you
int rowsAffected = ps.executeUpdate();
Gluing also breaks
Names with apostrophes, NULL values, dates and number formatting. .formatted() or text blocks don't fix it. It's still gluing.
Setters
setString, setInt, setLong, setDouble, setBoolean, setBigDecimal, setDate, setTimestamp, setObject, setNull.
The limit
? can only stand for a value. It can't be a column name, table name or ASC/DESC. See the gotcha below.
Core · CRUD

Five operations, one repeating shell

Every repository method has the same outer shell: open a connection, prepare the statement, catch SQLException, close everything. Only the middle changes. Notice how much repeats. That repetition is exactly what chapter 2 (Spring JDBC) removes.

mindmap
  root((Student CRUD))
    Create
      INSERT with 3 blanks
      executeUpdate gives 1
      Want the new id? RETURN_GENERATED_KEYS
    Read one
      WHERE id = ?
      if next then map row
      Optional - empty means not found
    Read all
      while next, add to list
      Empty list when no rows
    Update
      SET 3 values WHERE id
      4 blanks, order matters
      1 updated, 0 not found
    Delete
      WHERE id = ?
      1 deleted, 0 not found

// Every CRUD method in raw JDBC looks like this. Only the middle part changes.
public RESULT someOperation(...) {
    String sql = "...";                                       // 1. the SQL with ? blanks
    try (
        Connection connection = DriverManager.getConnection(URL, USERNAME, PASSWORD); // dial
        PreparedStatement ps = connection.prepareStatement(sql)                       // the form
    ) {
        // 2. fill the blanks:  ps.setString(1, ...); ...
        // 3. send it:          ps.executeUpdate()  or  ps.executeQuery()
        // 4. use the answer:   a count, or rows → objects
    } catch (SQLException e) {
        throw new RuntimeException("Failed to ...", e);       // don't swallow errors
    }                                                         // auto hang-up
}
public int save(Student student) {
    String sql = "INSERT INTO students(name, email, age) VALUES (?, ?, ?)";
    try (Connection connection = DriverManager.getConnection(URL, USERNAME, PASSWORD);
         PreparedStatement ps = connection.prepareStatement(sql)) {
        ps.setString(1, student.getName());
        ps.setString(2, student.getEmail());
        ps.setObject(3, student.getAge());
        return ps.executeUpdate();                 // 1 = saved
    } catch (SQLException e) {
        throw new RuntimeException("Failed to save student", e);
    }
}

// usage
if (repository.save(new Student("Rahul", "rahul@gmail.com", 24)) == 1) {
    System.out.println("Student saved successfully");
}
public long saveAndReturnId(Student student) {
    String sql = "INSERT INTO students(name, email, age) VALUES (?, ?, ?)";
    try (Connection connection = DriverManager.getConnection(URL, USERNAME, PASSWORD);
         PreparedStatement ps = connection.prepareStatement(sql, Statement.RETURN_GENERATED_KEYS)) { // "tell me the new id"
        ps.setString(1, student.getName());
        ps.setString(2, student.getEmail());
        ps.setObject(3, student.getAge());
        if (ps.executeUpdate() != 1) throw new RuntimeException("Student was not inserted");

        try (ResultSet keys = ps.getGeneratedKeys()) {   // a tiny ResultSet holding the new id
            if (keys.next()) return keys.getLong(1);
        }
        throw new RuntimeException("Generated ID was not returned");
    } catch (SQLException e) {
        throw new RuntimeException("Failed to save student", e);
    }
}
public Optional<Student> findById(Long id) {
    String sql = "SELECT id, name, email, age FROM students WHERE id = ?";
    try (Connection connection = DriverManager.getConnection(URL, USERNAME, PASSWORD);
         PreparedStatement ps = connection.prepareStatement(sql)) {
        ps.setLong(1, id);
        try (ResultSet rs = ps.executeQuery()) {
            if (rs.next()) return Optional.of(mapRow(rs));   // found it
            return Optional.empty();                          // normal "not found"
        }
    } catch (SQLException e) {
        // a broken database is NOT "not found", so don't return Optional.empty() here
        throw new RuntimeException("Failed to fetch student with ID " + id, e);
    }
}

private Student mapRow(ResultSet rs) throws SQLException {    // one row → one Student
    return new Student(rs.getLong("id"), rs.getString("name"),
                       rs.getString("email"), rs.getObject("age", Integer.class));
}

// usage
repository.findById(1L).ifPresentOrElse(System.out::println,
        () -> System.out.println("Student not found"));
public List<Student> findAll() {
    String sql = "SELECT id, name, email, age FROM students";
    List<Student> students = new ArrayList<>();
    try (Connection connection = DriverManager.getConnection(URL, USERNAME, PASSWORD);
         PreparedStatement ps = connection.prepareStatement(sql);
         ResultSet rs = ps.executeQuery()) {
        while (rs.next()) {              // finger moves down until false
            students.add(mapRow(rs));    // read columns → Student → add
        }
        return students;                 // empty list if the table is empty
    } catch (SQLException e) {
        throw new RuntimeException("Failed to fetch students", e);
    }
}
public int update(Long id, Student student) {
    String sql = "UPDATE students SET name = ?, email = ?, age = ? WHERE id = ?";
    try (Connection connection = DriverManager.getConnection(URL, USERNAME, PASSWORD);
         PreparedStatement ps = connection.prepareStatement(sql)) {
        ps.setString(1, student.getName());   // 1st ? → name
        ps.setString(2, student.getEmail());  // 2nd ? → email
        ps.setObject(3, student.getAge());    // 3rd ? → age
        ps.setLong(4, id);                    // 4th ? → id (the WHERE)
        return ps.executeUpdate();            // 1 = updated, 0 = no such student
    } catch (SQLException e) {
        throw new RuntimeException("Failed to update student with ID " + id, e);
    }
}
// Just run the UPDATE and check the count. Don't call findById() first:
// that's an extra trip, and the row can change between the two calls.
public int deleteById(Long id) {
    String sql = "DELETE FROM students WHERE id = ?";
    try (Connection connection = DriverManager.getConnection(URL, USERNAME, PASSWORD);
         PreparedStatement ps = connection.prepareStatement(sql)) {
        ps.setLong(1, id);
        return ps.executeUpdate();            // 1 = deleted, 0 = nothing matched
    } catch (SQLException e) {
        throw new RuntimeException("Failed to delete student with ID " + id, e);
    }
}

Why not check first, then update?

flowchart TD
  A["findById(1)"] --> B["Student exists"]
  B --> C["...another user deletes it..."]
  C --> D["UPDATE ... WHERE id = 1"]
  D --> E["0 rows. Your check was already stale"]
Two trips: slower, and the answer can change in between (a race condition).
flowchart TD
  A["UPDATE ... WHERE id = 1"] --> B{"rows affected?"}
  B -- "1" --> C["Updated"]
  B -- "0" --> D["Not found"]
One trip. The count is the answer. Only add an extra query when you truly need more detail. (Note: MySQL settings like useAffectedRows change whether "0" means "not matched" or "nothing changed".)
Core · closing resources

Hang up in reverse order

The three objects live inside each other, like nesting boxes. The connection creates the statement, and the statement creates the result set. You close the inner box first, then work outwards.

try-with-resources does this for you, in reverse order of how you declared them. Step through it.

Forget to close?
Leaked connections, too many open sessions, "Too many connections" errors, slowdown, transactions left open.
Old way
A finally block with three null checks and three nested try/catch. Works, but long and easy to get wrong.
Here vs later
In this plain project close() really ends the connection. With a connection pool (chapter 2), close() hands it back to the pool instead.

The one gotcha worth remembering

? protects values, not names

Wrong belief: "I use PreparedStatement, so I'm safe from injection everywhere." Placeholders only work for values. If a user picks the sort column and you glue it in, they control your SQL again.

✗ Unsafe
// sortColumn comes from the request
String sql = "SELECT id, name, email, age FROM students ORDER BY "
           + sortColumn;   // user can inject anything here
// and this does NOT work either:
// "... ORDER BY ?"  → ? can't stand for a column name
✓ Safe
Set<String> allowed = Set.of("id", "name", "age");
if (!allowed.contains(sortColumn)) {
    throw new IllegalArgumentException("Bad sort column");
}
String sql = "SELECT id, name, email, age FROM students ORDER BY "
           + sortColumn;   // only known-good words reach SQL

Rule: placeholders for values, an allow-list for anything structural (column, table, ASC/DESC).

Smaller traps

  1. Forgetting next(). The cursor starts above the first row. Reading before calling next() throws an error.
  2. Counting blanks from 0. setString(0, …) fails. JDBC numbers start at 1.
  3. Reading execute()'s false as "failed". It just means the first result is a count, not rows.
  4. getInt on an empty column. You silently get 0, a fake value. Use getObject("age", Integer.class).
  5. Passwords in code. Fine for learning. In real projects use environment variables or a secrets store, and keep them out of Git.
Test yourself · answer out loud before opening

Recall check

1. Why can't Java just call MySQL like a normal method?

They're separate programs, possibly on different computers. Java needs a connection over the network and a driver that speaks MySQL's protocol. A SQL string in Java is only text until it's sent.

2. What's the difference between the JDBC API and the JDBC driver?

The API is the standard set of interfaces your code uses (Connection, PreparedStatement, ResultSet). The driver is the database-specific implementation behind them (Connector/J for MySQL).

3. Which method for SELECT? For DELETE? What does execute() returning false mean?

executeQuery for SELECT, executeUpdate for DELETE. false from execute() means the first result is an update count or nothing. It doesn't mean it failed.

4. Predict: a fresh ResultSet has 2 rows. You call next() three times. What does each call return?

true, true, false. The cursor starts above row 1, moves to row 1, then row 2, then finds nothing.

5. The age column is NULL. What does getInt("age") give, and what should you use?

0. Use getObject("age", Integer.class), which gives null (or check wasNull()).

6. Name three problems with gluing values into SQL strings.

SQL injection, broken quotes (O'Brien), NULL handling, number/date formatting, poor readability.

7. update() returned 0. Is that an error?

No. No row matched the WHERE. Report "not found". A real database error would throw SQLException instead.

8. In what order are resources closed, and who does it?

ResultSet, then PreparedStatement, then Connection: reverse of creation. try-with-resources does it automatically in reverse declaration order.
